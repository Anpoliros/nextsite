# Docs

本目录是项目的文档入口，目标是让维护者和 coding agent 快速理解项目结构、模块边界、修改入口和验证方式。

文档不追求复刻源码目录，而是为源码提供可维护的导航层：读者应先通过 `MAP.md` 找到相关文档，再进入源码做具体修改。

## 文档目标

- 说明项目的主要目录、功能模块和工程流程。
- 记录核心模块的职责边界、数据模型、公共接口和构建产物。
- 帮助 coding agent 在修改前快速确认入口文件、影响范围和验证方式。
- 为后续文档扩展提供稳定规范，避免文档随功能增长而失控。

## 目录组织

```txt
docs/
  README.md   # 文档入口：说明目录职责、使用方式和集成方式
  MAP.md      # 文档地图：维护源码路径和文档路径的映射
  SPEC.md     # 文档规范：说明写作模板、更新规则和质量要求
  init.md     # 初始化指南：说明如何在任意项目中启动文档体系
```

后续可按源码主目录扩展：

```txt
docs/
  app/        # 对应 app/，记录页面、布局、路由和渲染策略
  components/ # 对应 components/，记录公共组件和关键交互组件
  lib/        # 对应 lib/，记录数据处理、Markdown、内容读取等核心逻辑
  content/    # 对应内容源和静态资源，记录内容模型与资源产物
  workflows/ # 记录开发、构建、部署、内容同步等流程
  decisions/ # 记录重要技术决策和迁移背景
```

## 使用方式

修改项目时，建议按以下顺序阅读文档：

1. 先读 `docs/MAP.md`，确认目标源码路径对应的文档。
2. 再读相关模块文档，理解职责边界、入口文件和风险点。
3. 修改源码后，根据 `docs/SPEC.md` 判断是否需要同步更新文档。
4. 最后在变更说明中记录已更新的文档或未更新的原因。

如果要把这套文档规范迁移到其他项目，先读 `docs/init.md`，再按项目目录改写 `MAP.md`。

## 集成方式

建议在 `AGENTS.md` 中只保留轻量规则，把详细规范放在本目录：

```md
## 文档维护规范

- 修改核心模块、公共组件接口、数据模型、构建流程或部署流程时，必须检查 `docs/`。
- 开始修改前，优先查看 `docs/MAP.md`，确认源码路径对应的文档。
- 文档写作、模板和更新规则见 `docs/SPEC.md`。
```

这样可以降低 `AGENTS.md` 的维护压力，同时让文档规范可以在不同项目之间复用。
